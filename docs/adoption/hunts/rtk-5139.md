# redux-toolkit#5139: an optimistic update replaced by a polling or refetch-on-focus fetch

Evidence for the Redux Toolkit maintainers, not a fix: a runnable reproduction, two failing tests and the sequence of
events and state changes asked for in the thread. Nothing here has been posted to reduxjs/redux-toolkit; the draft
comment is [rtk-5139-comment.md](rtk-5139-comment.md), for the owner to post.

- Issue: https://github.com/reduxjs/redux-toolkit/issues/5139 (open, label RTK-Query)
- Reproduction: [rtk-5139/repro/](rtk-5139/repro/) (standalone; it imports nothing from GenClass)
- Timeline harness and raw output: [rtk-5139/timeline/](rtk-5139/timeline/)
- Prepared 2026-10-25. Node 22.22.0, headless Chromium through Playwright 1.63.0, Linux.

## Summary

- **Verdict: not documented behaviour; a bug against the docs' stated purpose, by design rather than by a coding
  slip.** The docs give the purpose of an optimistic update as "the impression that their changes are immediate, even
  while the mutation request is still in flight", warn only about overlapping mutations, and say nothing about other
  fetches of the entry. In 2.13.0 any fulfilled fetch of the same cache entry replaces `data` with the server payload,
  and RTK keeps no record that an optimistic patch is pending, so it has nothing to re-apply. What the behaviour
  *should* be (re-apply, skip, or discard the fetch) is undecided in the thread, which is why this is evidence and not
  a PR.
- **Reproduced:** the Playwright test failed 10 of 10 runs with `pollingInterval: 100` and 10 of 10 with
  `refetchOnFocus`, and passed 10 of 10 for the control (neither); the Redux-only vitest gave the same result on each
  of 10 runs ([results/](rtk-5139/results/)). With a userland workaround applied ([workaround.patch](rtk-5139/workaround.patch)),
  both pass every time.
- **The sequence**, ms after the click (polling): `executeMutation/pending` +1, `queryResultPatched` +4 ("Edited 1"),
  the next poll's `executeQuery/pending` +64 and `executeQuery/fulfilled` +76 ("Original" again), 15 more polls with
  "Original", the PUT's `executeMutation/fulfilled` +2038, and "Edited 1" again from the first GET the server answered
  after the PUT (+2059), then the `invalidatesTags` refetch (+2060 to +2086).
- **What GenClass added beyond Redux DevTools: little, and it is said plainly below.** It labels each refetch with its
  cause (poll timer or the PUT's response), which RTK's actions do not carry, and its happens-before witness separates
  the two shapes of the bug: a fetch already in flight when the patch is applied (witnessed 10 of 10) and a fetch
  started after the patch (this issue: not witnessed, by definition). Three of its four findings were RTK bookkeeping,
  not bugs, and its generated regression test passes on the buggy app.

## The thread so far

- **#5139** (agusterodin, 2025-11-22): an optimistic update from a slow mutation is lost when a polling or
  refetch-on-focus fetch of a fast GET fulfills before the mutation finishes; the UI flickers. Two workarounds failed
  (skipping the query hook while a mutation is pending; a `merge` that keeps the cached data, which cannot read the
  store). The reporter attached two videos and linked a stripped-down playground branch, but the real endpoints need
  authentication and a database, so there was no runnable repro. markerikson the same day: he tried local changes
  (tracking a "data version" in the cache), wrote "Now I'm actually a bit confused and want to take a step back :)",
  and asked: "Can you talk me through both the actual
  behavior you're seeing, and what you would _expect_ or _want_ the behavior to be instead? Like, the sequence of
  events and state changes?" and "Would you expect the polling refetch to be ignored completely and _not_ update the
  state?" Label added 2025-12-16. The reporter answered on 2025-12-17 in prose (the optimistic value should persist
  while the mutation runs; fresh data should not be thrown away; re-apply the patches of in-flight mutations on top of
  it). No reply since; no linked branch or PR.
- **#5103** (Brma1048, 2025-10-10) was not closed without comment: it was converted to
  [discussion #5105](https://github.com/reduxjs/redux-toolkit/discussions/5105) the next day. There markerikson wrote
  (2025-10-11): "An optimistic update (ie `api.util.updateQueryData()`) will be applied immediately, separate from the
  fact that you've kicked off a refetch," and that "the data in the cache should contain the optimistic value, and be
  available for use in the UI." On 2025-11-06 he "tried throwing the discussion into Claude" and posted its analysis,
  which says "This is **NOT a bug** - it's the **expected behavior** of RTK Query" and suggests not invalidating while
  a send is pending, invalidating after success, or a `merge`. He added no verdict of his own; two weeks later, in
  #5139, he wrote the "step back" comment above. No reply in the discussion after that.

## What the code does (2.13.0)

Paths are under `packages/toolkit/src/query/` at tag `v2.13.0`.

- **The refetch.** Polling (`core/buildMiddleware/polling.ts` line 115, in `startNextPoll`) and focus/reconnect
  (`core/buildMiddleware/windowEventHandling.ts` line 56, in `refetchValidQueries`) both dispatch `refetchQuery`
  (`core/buildMiddleware/index.ts` lines 146-161): `initiate(querySubState.originalArgs, { subscribe: false,
  forceRefetch: true })`. Tag invalidation uses the same function (`core/buildMiddleware/invalidationByTags.ts` line
  134). In the action log all three look identical.
- **The optimistic update.** `updateQueryData` (`core/buildThunks.ts` lines 407-463) computes Immer patches and
  dispatches `queryResultPatched` with them in its payload (`core/buildThunks.ts` lines 370-372), whose reducer applies
  them to `substate.data` (`core/buildSlice.ts` lines 359-371). After that RTK keeps them nowhere: not in the store,
  not in middleware state, and nothing ties them to the mutation. Only the caller holds the returned `PatchCollection`
  (`patches`, `inversePatches`, `undo`).
- **The overwrite.** `writeFulfilledCacheEntry` (`core/buildSlice.ts` lines 225-281) returns early only when the
  response's `requestId` is not the entry's current one (line 235); otherwise `data` becomes
  `copyWithStructuralSharing(old, payload)` (or the endpoint's `merge`). Mutations do not take part in that check.
- **Two guards that show up in the timeline.** A refetch is skipped while a fetch of the same entry is in flight
  (`condition` returns false for status `pending`, `core/buildThunks.ts` lines 946-949; the action is
  `executeQuery/rejected` with `meta.condition`), and with the default `invalidationBehavior: 'delayed'` tag
  invalidation waits until no request is pending (`invalidationByTags.ts` lines 103-108).

So any fetch of the entry that fulfills while the mutation is pending replaces the optimistic data. There are two
shapes, with the same cause:

1. **A fetch already in flight when the patch is applied** (#5103 / #5105): its response is the server's state from
   before the click.
2. **A fetch started after the patch, while the mutation is pending** (#5139): its response is the server's state
   before it applied the mutation.

By code reading (not run here), `refetchOnReconnect` and a manual `refetch()` take the same path. A refetch from tag
invalidation (another mutation's `invalidatesTags`, or `api.util.invalidateTags`) cannot *start* while this mutation
is pending under the default `'delayed'` behaviour, because the pending mutation counts as a pending request
(`invalidationByTags.ts` lines 49-54 and 103-108); it hits only if it was already in flight (shape 1) or with
`invalidationBehavior: 'immediately'`.

## Bug or documented behaviour?

**Not documented behaviour; I call it a bug.** Plainly:

- The docs ([manual-cache-updates.mdx](https://github.com/reduxjs/redux-toolkit/blob/v2.13.0/docs/rtk-query/usage/manual-cache-updates.mdx),
  "Optimistic Updates", lines 50-71) give the purpose of the update as "the impression that their changes are
  immediate, even while the mutation request is still in flight". The recipe's steps mention a re-fetch only as a
  way to recover from a failed mutation, not other fetches of the entry while it is pending. The one caveat is a tip
  about many mutations "in short succession causing overlapping requests" and `.undo` races. Nothing in that page,
  `api-slice-utils.mdx` or `polling.mdx` says a polling, focus or other fetch replaces a pending optimistic update.
- The maintainer statements do not settle it. In #5105 he wrote that the update "will be applied immediately,
  separate from the fact that you've kicked off a refetch. So, the data in the cache should contain the optimistic
  value", which describes the state before the refetch lands (2.13.0 does exactly that); it does not say what should
  happen when it lands. The "expected behavior" text in #5105 is an AI analysis he posted without endorsing.
- The tests do not cover it. `tests/optimisticUpdates.test.tsx` "updates hook data while a refetch is in flight"
  (lines 195-246) applies a patch during an in-flight refetch, resolves the refetch, and asserts nothing afterwards; no
  test combines optimistic updates with polling or focus.
- It is not a slip in one line: the store keeps one `data` per entry and has no notion of pending patches, so a
  fulfilled fetch replacing them follows from the design. Calling it "documented" would need a sentence the docs do not
  have; a maintainer could fairly call it a documentation gap instead of a bug, and the docs need that sentence either
  way. Which behaviour is right (re-apply the pending update on the fresh data, skip or defer the refetch, or discard
  the response) is a design decision for the maintainers; markerikson's question "Would you expect the polling refetch
  to be ignored completely" is still open.

### What GenClass added beyond Redux DevTools

Honestly, little for this issue: the Redux action log with the cached value after each action is the evidence the
maintainers asked for, and DevTools shows it too. What GenClass added:

- **The cause of each refetch.** Every `executeQuery/pending` from polling, focus and invalidation carries the same
  `forceRefetch: true, subscribe: false`. GenClass labels polls "via timer 100ms" and the invalidation refetch "via
  PUT /api/items/:id" with the click at its root. It recorded no cause for the focus refetch (the log's
  `__rtkq/focused` just before is clearer), and when delayed invalidation is released by a poll's end it names that
  poll as the cause.
- **Network times next to the actions.** In 9 of 10 polling runs the overwriting GET was sent 22 to 88 ms after the
  click, so it is not a stale response that was already on the way. The `pending` action a few ms earlier says nearly
  the same, and the browser's Network panel shows request times too.
- **The two shapes, told apart.** Its `overwrote-newer` witness fires when a response lands over a write made after
  that request started. It fired 10 of 10 when a fetch was in flight at the click (#5105's shape: older data put over
  newer, by the page's own order) and never when the fetch started after the patch (this issue: the fetch is newer on
  the page; it is stale only relative to the server's pending write, which no client-side ordering can see).

What did not help:

- 3 of 4 findings are RTK bookkeeping: the invalidation refetch's `pending` write (attributed to the PUT's response
  chain) lands on `status`, `requestId` and `startedTimeStamp` after a newer GET (a poll or the focus refetch) wrote
  them. True happens-before facts, not bugs.
- The Playwright test `genclass_explain` generated for f4 (its text is in `timeline/output/mcp-explain-f4.txt`)
  **passed 5 of 5 on the buggy app** (run against the repro with GenClass booted; one change: wait for the agent
  object, because `genclass-boot.ts` connects after `load`; the run log was not kept). It
  asserts the witness, which depends on the click landing while a poll is in flight, and a delivery-order replay does
  not recreate that timing. It also waits twice for a quiet point that a polling page never reaches (15 s each). The
  repro's own Playwright test, which asserts what the user sees, is the regression test to use.
- `genclass_explore` and `genclass_replay` were not run: explore compares final states, and the final state here is
  right (the bug is transient); a polling page never reaches the quiet point both rely on.

### GenClass issues found (this repository, not RTK)

- `src/agent/schedule.ts` line 212 keys a request `<parent key>~hedge` (or `~retryN`) whenever its causal parent is a
  request with the same signature. RTK's delayed invalidation refetch, started from a poll's response handler, was
  labelled `GET /api/items#22~hedge` although GenClass sent nothing (observe mode, no model; the step has no
  "(hedge)" detail). The request is the app's own; only its label is wrong, but an agent reading it would think
  GenClass acted.
- The agent link sends a run's steps at a quiet point, on `pagehide`, and once when the bridge answers the hello
  (`src/agent/index.ts`, `flushSteps`). A polling page never goes quiet (the settle time is 400 ms, the poll 100 ms),
  so while it is open the bridge has its witnesses but none of its later steps. In the batch
  where the harness closed the page without a `pagehide`, `genclass_status` listed those runs with "0 actions, 0
  requests" and `genclass_explain` had no steps, no replay and no test.
- The generated regression test asserts a timing-dependent witness and passes on the bug (above).
- Witnesses on a data-fetching library's bookkeeping fields are noise for an agent (above).

## Fix directions (no PR)

A and B need RTK to know that a cache entry has pending optimistic updates, and A also which mutation each belongs to;
RTK knows neither today (a `dispatch(updateQueryData(...))` inside `onQueryStarted` is not linked to the mutation's
`requestId`). C can work with a per-entry data version alone; D needs no code.

| direction | what changes | for | against |
|---|---|---|---|
| **A. Re-apply pending optimistic updates on fulfilled data** | Keep, per cache entry, the updates of in-flight mutations (in middleware state, like the polling timers); after a fulfilled write, re-apply them; drop them when the mutation settles (success: the server's value comes from the `invalidatesTags` refetch if there is one, else from the next fetch or a pessimistic write of the response; failure: drop instead of applying `inversePatches` to data that has changed). | What the reporter suggested and what the docs' stated purpose implies; fresh data for other fields is kept; covers both shapes, every refetch source, and overlapping mutations. Apollo Client keeps optimistic results in a layer above its cache until the mutation settles, so results written meanwhile do not remove them. | The largest change. Immer patches are path based: re-applied to a new payload (an array reordered, an item removed) they can hit the wrong element, so recipes (functions) may have to be kept instead; `undo()` changes meaning; needs a way to tie an update to its mutation (for example a lifecycle helper). |
| **B. Skip or defer refetches of an entry with pending optimistic updates** | `startNextPoll` and `refetchValidQueries` (and possibly invalidation) skip such entries, or postpone until the mutation settles. | Small and local; no reducer change. | Does not cover shape 1 (a fetch already in flight); other fields of the entry stay stale for the whole mutation; a long mutation silences polling. |
| **C. Discard a fulfilled response that would replace a pending update** | `writeFulfilledCacheEntry` ignores it (a data version bumped by the patch, or "a mutation that patched this entry is pending"). | Simple to state; markerikson already tried a data version. | The reporter does not want fresh data dropped; the next poll may fetch the same thing again; a version alone covers shape 1 only. |
| **D. Document it** | Say in "Optimistic Updates" that a fetch of the same entry (polling, `refetchOnFocus` / `refetchOnReconnect`, a manual `refetch`, an invalidation refetch already in flight) that fulfills while the mutation is pending replaces the optimistic update, and show a workaround. | No code change; settles the "is it expected" question. | The flicker stays. |

A userland workaround in the spirit of A, the repro's half of [workaround.patch](rtk-5139/workaround.patch) (with it,
the vitest passed 3 of 3 on 10 runs and the Playwright test 30 of 30):

```ts
// api.ts: keep the recipe of each in-flight optimistic update
export const pendingUpdates = new Map<string, (draft: Item[]) => void>()

renameItem: build.mutation<Item, Pick<Item, 'id' | 'name'>>({
  query: ({ id, name }) => ({ url: `items/${id}`, method: 'PUT', body: { name } }),
  async onQueryStarted({ id, name }, { dispatch, queryFulfilled, requestId }) {
    const recipe = (draft: Item[]) => {
      const item = draft.find((i) => i.id === id)
      if (item) item.name = name
    }
    dispatch(api.util.updateQueryData('getItems', undefined, recipe))
    pendingUpdates.set(requestId, recipe)
    try {
      await queryFulfilled
    } catch {
      dispatch(api.util.invalidateTags(['Item'])) // not undo(): the data under the patch may have changed
    } finally {
      pendingUpdates.delete(requestId)
    }
  },
  invalidatesTags: (_result, _error, { id }) => [{ type: 'Item', id }],
}),

// store.ts: after any getItems fetch fulfills, run the pending recipes again (placed before api.middleware)
const reapplyPendingUpdates: Middleware = (store) => (next) => (action) => {
  const result = next(action)
  if (api.endpoints.getItems.matchFulfilled(action))
    for (const recipe of pendingUpdates.values()) store.dispatch(api.util.updateQueryData('getItems', undefined, recipe) as any)
  return result
}
```

Limits: the re-apply is a second dispatch, so a plain `store.subscribe` listener can see the server's value once
before it (React did not render it: the Playwright test, which records every DOM change, passed 30 of 30); the recipe must be safe to run on fresh data (find by id, not by
index); it handles one endpoint and argument.
