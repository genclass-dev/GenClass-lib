The problem

The worst bugs never throw an error.

A customer taps "Pay" twice on a slow checkout. A slow response lands after a fast one. An endpoint starts failing at 2 a.m. and the app keeps polling it. Nothing crashed, so your error monitor sees nothing. GenClass watches the timing and the data as well as the exceptions, and reports what it finds with the evidence.

Duplicate submits

A double-tap on a slow checkout. GenClass flags the repeat and names the evidence: the request already in flight and how far apart the clicks were. Model 0.2.0 sees 3 in 4 on real apps it never trained on.

Failure storms

An API that starts failing while the app keeps polling it. GenClass reports the failure streak and the baseline it broke, whether or not the app shows an error.

Stale responses

Results for "pa" under a box that says "paris". GenClass flags the old response landing over newer data. Model 0.2.0 sees 30% of these on held-out real apps; guard mode, opt-in, can drop that write.

Write races

A server echo that would overwrite what the user just typed. GenClass flags it and shows what would be replaced.

Broken state

It learns relations your data keeps, like a cart total matching its lines, and reports when one breaks. This is its weakest class today: 6% of broken state on held-out real apps (model 0.2.0, balanced).

Slow and flaky calls

Latency far off the learned baseline, and one-off failures a retry would survive. GenClass reports both. The retry itself is a heal-mode action, experimental and its least precise.

Nothing for a while is normal

Observe mode reports only salient situations: a response landing over newer data, a repeat, a failure streak, a broken relation, an error. The first response of each kind after a page load is never a delivery decision, because the runtime first has to see what that request writes.

Some flags will be wrong

Expect 1 to 4 false flags per 100 decisions where nothing was wrong, more in some apps (model 0.1.0; not re-measured for 0.2.0). Identical lines within a minute are folded into one with a count. requests.ignore drops traffic you do not want observed.

Reports stay in the browser

A report is a console line in the user's browser, and in production that is not your console. Add a sinks entry to send each report to your logging or Sentry (below). The anonymous diagnostics go to the GenClass maintainers, not to you.

The overlay on localhost

Alt+Shift+G opens the devtools overlay; init loads it in development only. rt.explain(id) returns the exact text the model read, and rt.audit() exports every decision.

Already have Sentry or PostHog?

Keep them; GenClass is the detector they do not have.

Error monitors see exceptions, failed requests and slow spans. Session replay shows what the user saw. Neither knows that a response was stale or that a POST was a duplicate, because nothing threw. GenClass decides that on the device and hands each report to the tools you already open.

When not to use it

Skip GenClass if

  • Your site is mostly static. With no requests that write state there is nothing to decide, and the model download would be the only effect.
  • Every request is already idempotent and deduplicated. Idempotency keys on the server and request deduplication in the client (TanStack Query and SWR do this for reads) remove most of what GenClass would report.
  • Your users are on 2 GB phones and you cannot set a floor. The worker holds 190 to 280 MB while the model is loaded, and the default loadIf has no device floor. model: { loadIf: { minDeviceMemoryGB: 4 } } skips it there; without that, do not install it on those pages.
  • You run a strict Content-Security-Policy and cannot self-host. The model and ONNX Runtime come from cdn.jsdelivr.net; if the policy blocks them, GenClass observes without a model and detects nothing. Self-hosting is one command and about 24 MB of files on your origin.
  • You need bugs fixed today, not reported. At the shipped setting guard acts on under 8% of the cases where acting would help, and six demo apps under chaos show the same bug rate with GenClass on or off.
How it works

A model in the browser, deciding at the network boundary.

01

Observe

One line patches fetch, XHR, WebSocket and EventSource, and finds React and Redux state automatically, and Zustand with its devtools middleware.

02

Triage

Cheap facts are computed for everything. Only salient situations, like a response landing over newer data, reach the model. There is no list of known bugs in the code.

03

Decide on-device

A 10 MB model in a Web Worker returns a calibrated diagnosis and action. No server, no API key.

04

Report, or act if you opt in

Observe reports in plain English with the evidence. Guard can drop a stale write or merge a duplicate when its gate clears, with undo and an audit trail. At the shipped setting that is rare: under 8% of the cases where acting would help.

Install

One line, first in your app.

Observe mode is the default: it reports and changes nothing. Switch to guard when you trust what it sees.

// npm i @genclass/runtime, then first line of src/main.ts
import "@genclass/runtime/auto";          // observe
// import "@genclass/runtime/auto/guard";   // let it act
// instrumentation-client.ts (project root)
import "@genclass/runtime/auto";
<!-- first in <head>, no build step; keep the version pinned -->
<script src="https://cdn.jsdelivr.net/npm/@genclass/runtime@{{rt}}"></script>
# detects your framework, shows the diff, asks, then writes
npx @genclass/runtime init
npx @genclass/runtime init --mode guard
npx @genclass/runtime remove   # undo exactly what init added

What it costs

+98 KB of JavaScript on first load. About 13 MB downloaded once, at idle, on WASM (the 10 MB model plus ONNX Runtime), 18 MB on WebGPU, then cached. 190 to 280 MB of memory in a Web Worker while the model is loaded. No measurable change to the load event, LCP or long tasks on a production Next.js site (0.1.0-beta.3). There is no device floor by default: model: { loadIf: { minDeviceMemoryGB: 4, saveData: "skip" } } skips the model on small devices, and model.unloadAfterIdleMs frees the worker. The measurements.

Diagnostics are on by default

On public hosts the runtime sends anonymous diagnostics to the GenClass maintainers: decision counts, versions, your hostname and id-normalised paths, never page text. It is off on localhost and private hosts. One line turns it off: GenClass.init({ telemetry: false }), or npx @genclass/runtime init --no-telemetry. What is sent.

FAQ

Questions

Is GenClass free?

Yes. The runtime is open source under Apache-2.0 and free, including in commercial apps, with no usage limits. Cloud and Enterprise are planned paid products for teams; they have no customers yet.

Does it need an account or an API key?

No. One script tag or import "@genclass/runtime/auto" is all it takes. The model runs on the device.

Is the demo above real?

Yes. This page loads @genclass/runtime@{{rt}} from npm and runs the model on your device. The demo calls a real endpoint on this site; the page asks for the delays so the race is reproducible. It runs guard mode with its gain margins at 0 and the eager profile so you can see it act. The shipped defaults, observe mode and the balanced profile, report and do not act; the demo can run with them too. Telemetry is off on this site.

Where do the reports go in production?

To the end user's browser console, which you do not see. Add a sinks entry to forward each report to your logging, Sentry or PostHog (three lines, above). The anonymous diagnostics go to the GenClass maintainers' collector to improve the model, not to you.

Where does the model run?

In your users' browsers, inside a Web Worker on WebGPU or WASM. No server, no inference fees, and it keeps working offline once cached.

Will it break my app?

The default mode only observes. Across 7 frameworks and 15 data layers it introduced no bugs in 3,510 runs and took no non-passive action on correct apps in 1,760 guard and heal runs. ?genclass=off turns it off instantly.

How often does it act today?

Rarely, by design. It is tuned to almost never be wrong when it acts, so at the shipped setting guard acts on 7.5% of the real cases where acting would help (model 0.2.0, balanced). The benchmarks show the exact trade-off.

Will it spam my console?

In observe mode expect 1 to 4 false flags per 100 decisions where nothing was wrong (model 0.1.0; not re-measured for 0.2.0), and more on some patterns: one held-out app had a quarter of its clean decisions flagged on a single field. On the compatibility matrix's correct apps, 49 of 319 findings in 880 runs were false, 45 of them "work is firing far more often than usual" on a page that polls and fans out. Identical lines within a minute are folded into one. requests.ignore drops traffic you do not want observed, and raising policy.thresholds.report trims the rest.
