# Measured: the usual fixes for stale search results and double submits

Generated by `report.mjs` from `results/raw/` (do not edit by hand). Seeds per strategy and profile: off 1 to 200, model 1 to 50, skipped 1 to 50. Profiles run: off: fast, jittery, lossy, tail; model: fast, jittery, lossy; skipped: fast, jittery, lossy.
How to run it again: [README.md](README.md).

## Setup

- **Pages.** One small page per strategy, written for this bench (`src/`), production builds (esbuild). Search pages send one request per keystroke unless the strategy says otherwise; the API echoes the query, and the page shows the results with the query they are for. Submit pages load the open tickets, then show a form with a Create button.
- **Server** (`server.mjs`): HTTP/2 on 127.0.0.1. Each request's latency is drawn from the run's seed, the profile and the request itself, so the request for a given query takes the same time whatever fix the page uses. Profiles: **fast**, latency uniform 20 to 60 ms, answered in request order; **jittery**, latency uniform 50 to 900 ms, each request on its own, so answers can arrive in any order; **lossy**, latency uniform 50 to 900 ms, each request on its own, so answers can arrive in any order, 5% of requests answered 503 and not processed; **tail**, latency uniform 50 to 900 ms, each request on its own, so answers can arrive in any order, except 10% of requests, which take 1500 to 4000 ms.
- **User** (Playwright, Chromium): types a two-word query (20 queries) with 60 to 150 ms between keys and a pause of 150 to 1200 ms before the second word, as people do when they glance at the first results; or double-clicks Create with 0 to 150 ms between the clicks (real mouse events at the button's position, so a disabled button really ignores the second click). All drawn from the seed: every strategy and condition sees the same user in a seed.
- **End of a run**: nothing in flight, no new request and no change on the page for 1000 ms, and nothing marked busy (a library waiting to retry counts as busy); at most 15 s after the last key or click.
- **Wrong final state.** Search: the results shown are for another query than the one typed (stale), an error is shown although the typed query's last answer succeeded (stale error), or nothing is shown. An error after the typed query's own request failed is the truth and counts as "error shown", not wrong. Submit: more than one ticket created.
- **Time to correct results**: from the last keystroke to the moment the results for the typed query appear for good (runs that end correct). Submit: from the first click to the first "Created" message.
- **GenClass conditions**: the one script tag first in `<head>` (the runtime built from this repository), `mode: "observe"`, `telemetry: false`, measured visual checks off (127.0.0.1 is a development host, where they would start; they never feed a detection). **model**: the default model loaded from this machine (`preload: "eager"`), and the user starts once it is ready; the default `aggressiveness` (balanced). **skipped**: `model: { loadIf: () => false }`, which is what a device with 2 GB of memory or less, or a Save-Data connection, gets by default.
- **Versions**: @genclass/runtime 0.3.0-beta.1 at commit `3fcdac5`, model @genclass/runtime-model@0.2.0 (genclass-runtime-r17 2.0.0-rc4t), React 19.3.1, TanStack Query 5.104.5, SWR 2.5.1, RxJS 7.8.2, Vue 3.5.44, Svelte 5.57.2, Playwright 1.63.0, Chromium 153.0.8010.12, Node v22.22.0.
